Chapter 01

What is
CuTe DSL?

CuTe DSL is a Python-embedded domain-specific language that lets you write GPU kernels using the same powerful CuTe abstractions as CUTLASS C++ — but from Python, with JIT compilation to CUDA PTX/SASS.

🐍

Python-First Authoring

Write kernel logic in pure Python. No CUDA C++ required. Decorators drive code generation.

⚡

JIT & AOT Compilation

Kernels compile Just-In-Time on first call, or Ahead-Of-Time for deployment.

🔷

CuTe Layout Algebra

First-class Layouts and Tensors describe hierarchical data mappings with compile-time shapes.

🧩

Tensor Core Intrinsics

Direct access to MMA (matrix multiply-accumulate) instructions on Ampere, Hopper, Blackwell.

🔁

Pipeline Primitives

Built-in async copy and software pipelining utilities to overlap data movement with compute.

# A minimal CuTe DSL kernel
import cute

@cute.jit
def scale_kernel(tensor, alpha):
    # Each thread handles one element
    tid = cute.thread_idx().x
    tensor[tid] = tensor[tid] * alpha

# Launch it from Python — compiles on first call
scale_kernel[128, 256](my_tensor, 2.0)
Key insight: The @cute.jit decorator traces your Python function and emits MLIR/LLVM IR that maps directly to GPU PTX. Your Python code is a specification, not runtime logic.

CuTe DSL sits at the top of the CUTLASS software stack, providing the highest-level entry point while remaining fully composable with lower layers.

The compilation pipeline uses NVIDIA's MLIR dialect (built into CuTe DSL) to lower Python kernel abstractions through multiple IR levels before generating native GPU instructions.

❌ Without CuTe DSL (CUDA C++)

// Manual tiling, index math, MMA calls
__global__ void gemm_kernel(
  half* A, half* B, float* C,
  int M, int N, int K) {
  // ~200 lines of layout math,
  // shared memory management,
  // PTX MMA intrinsics...
}

Requires deep CUDA expertise. Brittle to hardware changes. Hard to experiment with tiling strategies.

✅ With CuTe DSL (Python)

# Expressive, composable abstractions
@cute.jit
def gemm(A, B, C):
  mma = cute.MMA(
    shape=(16,8,16),
    dtype="fp16"
  )
  # Tiling, pipelining, MMA —
  # all in readable Python
  cute.gemm(mma, A, B, C)

Readable and hackable. Same performance as hand-tuned C++. Rapidly experiment with different tile sizes and data types.

Chapter 02

Layouts &
Tensors

The core abstraction in CuTe is the Layout — a function from a logical coordinate space to a linear memory offset. Pair a Layout with a data pointer and you get a Tensor.

What is a Layout?

A Layout encodes both the shape of a tensor (how many elements in each dimension) and the stride (how many elements to skip in memory to advance one step in each dimension).

# Layout(Shape, Stride)
# A 4×8 matrix, row-major:
layout = cute.Layout((4,8), (8,1))
#  coord (2,3) → offset 2*8 + 3*1 = 19

# Column-major (Fortran order):
layout_col = cute.Layout((4,8), (1,4))
#  coord (2,3) → offset 2*1 + 3*4 = 14
Power of layouts: Transposing a matrix is just swapping strides — no data movement. The hardware sees different access patterns from the same memory.

Layout Visualization

4×8 matrix — colors show logical rows mapping to linear memory

Row-major: stride = (8, 1) — rows are contiguous in memory

Tiling divides a large matrix into smaller blocks (tiles) that fit in shared memory or registers. CuTe makes tiling composable: a tile is just a sub-Layout of the original.

Each color represents a distinct 2×2 tile. In CuTe, you partition the layout into sub-layouts for each CTA (thread block).

cute.local_tile(tensor, tile_shape, tile_coord)

Creating Tensors

# Make a tensor from a pointer + layout
A_tensor = cute.make_tensor(A_ptr, 
  cute.Layout((M, K), (K, 1)))  # row-major MxK

# Partition across a thread block
tA = cute.local_partition(A_tensor, 
  thr_layout, cute.thread_idx())

Composing Layouts

# Hierarchical layout: describes how a CTA tile
# is subdivided across warps → threads → regs
atom_layout = cute.Layout(
  ((2,2), (4,8)),   # shape: warps × threads
  ((16,1), (4,32))  # strides into shared memory
)

# CuTe evaluates the composed offset at compile time
offset = atom_layout[warp_id, thread_id]
Compile-time vs runtime: When layout dimensions are known at compile time (Python integers), CuTe emits specialized PTX with no index math overhead. Runtime shapes still work — they just emit more general code.

When you call a @cute.jit kernel for the first time, Python traces through your function, emitting MLIR that is then lowered to CUDA PTX and compiled by nvcc. Subsequent calls reuse the cached binary.

🎯 Specialization

Each unique combination of tensor types, shapes, and kernel configs produces a distinct compiled binary — maximizing hardware utilization with zero runtime dispatch overhead.

⚙️ JIT Arguments

Use cute.Constexpr to mark arguments that should be specialized at compile time, enabling shape-specific code generation for tiling and loop unrolling.

# Constexpr arguments → compile-time specialization
@cute.jit
def tiled_copy(
    src: cute.Tensor,
    dst: cute.Tensor,
    tile_m: cute.Constexpr,   # ← baked into PTX
    tile_n: cute.Constexpr    # ← baked into PTX
):
    # Tile sizes are compile-time constants here
    tile = cute.make_shape(tile_m, tile_n)
    ...

CuTe DSL caches compiled kernels to disk so re-running a script doesn't recompile. The cache key includes the function source, argument types, compile options, and GPU arch.

📦

Persistent Disk Cache

Compiled .cubin / PTX is stored under ~/.cache/cutlass_dsl/ keyed by a hash of the kernel signature and options.

🔑

Cache Invalidation

Any change to the kernel source, input dtype, tile size, or CUDA arch automatically invalidates the cache and triggers recompilation.

🚀

Warm Startup

Production deployments hit the cache on every run. First-time compilation is typically 2–10 seconds; cached runs add <1ms overhead.

Ahead-Of-Time (AOT) compilation pre-compiles kernels into shared libraries (.so) that can be loaded without Python or CUDA toolkit at runtime. Ideal for production serving.

# AOT: compile once, ship a .so
from cute.aot import compile_to_library

compile_to_library(
    kernel_fn=my_gemm_kernel,
    args_signature=[
        cute.TensorType(dtype="fp16", rank=2),
        cute.TensorType(dtype="fp16", rank=2),
        cute.TensorType(dtype="fp32", rank=2),
    ],
    output_path="./libmy_gemm.so",
    arch="sm_90"  # Hopper
)
TVM FFI integration: CuTe DSL can also emit compiled kernels as TVM PackedFunc objects, enabling seamless integration into TVM-based runtimes and model compilers like Apache TVM or MLC-LLM.
Chapter 04

GEMM &
Tensor Cores

Matrix Multiply-Accumulate (MMA) operations are the workhorses of modern AI. CuTe DSL exposes tensor core MMA atoms with a clean Python API that maps 1:1 to hardware instructions.

A single MMA atom computes D = A × B + C using tensor cores. On Hopper (SM90), the warp-group MMA operates on 64×8×16 tiles per instruction.

×
B (K×N)
+
C → D (M×N)

Each cell represents a tile of values. Animation shows tensor core accumulation.

Ampere SM80

16×8×16 MMA atoms for FP16/BF16. Uses m16n8k16 WMMA instruction family.

Hopper SM90

Warpgroup-level 64×8×16 atoms. Adds FP8 support. Uses new wgmma async instruction family.

Blackwell SM100

tcgen05 MMA family. Adds TF32, I8, E4M3/E5M2 FP8 variants. Cluster-aware scheduling.

Selecting an MMA Atom

import cute
from cute.nvgpu.warpgroup import MMA_Atom

# Select a Hopper wgmma atom: FP16 in, FP32 accumulate
mma_atom = MMA_Atom(
    opclass=cute.OpClassTensorOp,
    arch=cute.SM90,
    shape=(cute.m64, cute.n8, cute.k16),
    dtype_AB=cute.float16,
    dtype_C=cute.float32,
)

Tiled MMA & Main Loop

# Scale the atom across a CTA tile
tiled_mma = cute.TiledMMA(
    mma_atom,
    atom_layout=cute.Layout((1,1,1)),  # warp layout
    perm=cute.Layout((1,1,1))
)

# Partition A and B across threads
thr_mma = tiled_mma.get_thread_slice(cute.thread_idx())
tCrA = thr_mma.partition_A(sA)  # registers for A
tCrB = thr_mma.partition_B(sB)  # registers for B
tCrD = thr_mma.partition_C(gC)  # accumulator regs

# Main K-loop: accumulate MMA results
for k in cute.range(K_tiles):
    cute.gemm(tiled_mma, tCrD, tCrA[k], tCrB[k], tCrD)

Software
Pipelining

The key to peak GPU utilization is hiding memory latency by overlapping async data loads with tensor core computation. CuTe DSL provides pipeline primitives that make this pattern concise and correct.

A 2-stage pipeline keeps one tile computing while the next tile is loading from global memory — doubling effective bandwidth utilization.

Click Animate to see the pipeline
TMA (Tensor Memory Accelerator): On Hopper and Blackwell, TMA hardware can move entire tiles between global and shared memory autonomously — freeing all threads to stay in the compute stage. 
from cute import pipeline

# Create a 2-stage async pipeline (Hopper TMA)
pipe = pipeline.PipelineTmaAsync(num_stages=2)

# Prologue: prefetch first tile
pipe.producer_acquire(0)
cute.cp_async_tma(tma_load, sA[0], gA[0])
pipe.producer_commit(0)

# Main loop: overlap load[k+1] with compute[k]
for k in cute.range(K_tiles):
    stage = k % 2
    next_stage = (k + 1) % 2

    # Issue next async load (producer)
    if k + 1 < K_tiles:
        pipe.producer_acquire(next_stage)
        cute.cp_async_tma(tma_load, sA[next_stage], gA[k+1])
        pipe.producer_commit(next_stage)

    # Wait for current tile, then compute (consumer)
    pipe.consumer_wait(stage)
    cute.gemm(tiled_mma, acc, tCrA[stage], tCrB[stage], acc)
    pipe.consumer_release(stage)

# Epilogue: write accumulators to global C
cute.copy(tCrD, gC)

Architecture
Support

CuTe DSL 4.0 targets three NVIDIA GPU generations, each adding new MMA data types and hardware features that map directly to Python API additions.

Architecture Compute Cap. MMA Dtypes Key Features Status
NVIDIA Ampere SM80 FP16 BF16 Async copy, 3rd-gen tensor cores Supported
NVIDIA Hopper SM90 FP16 BF16 FP8 TMA, wgmma, distributed shared mem Supported
NVIDIA Blackwell SM100 FP16 BF16 TF32 I8 F8 tcgen05, cluster launch ctrl, 5th-gen TC Supported

Platform Requirements

Python Version

Python 3.12 only. The DSL uses new typing features and metaclass behavior from 3.12.

CUDA Driver

Driver version 575.51.03 or later required (matches CUDA Toolkit 12.9).

Platform

Currently Linux x86_64 only. Windows and ARM support planned for future releases.

Framework Integration

CuTe DSL kernels can be called directly from PyTorch, JAX, or any framework that provides raw CUDA tensor pointers.

# PyTorch integration — pass tensors directly
import torch

A = torch.randn(1024, 1024, dtype=torch.float16, device='cuda')
B = torch.randn(1024, 1024, dtype=torch.float16, device='cuda')
C = torch.zeros(1024, 1024, dtype=torch.float32, device='cuda')

# CuTe DSL accepts torch tensors natively
my_gemm_kernel[grid, block](A, B, C)
